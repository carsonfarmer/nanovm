# Integrated Linux measurements, 2026-11-16

The integrated trim candidate serves useful stateful workloads. Its three-round
HTTP matrix completed without failed measured requests. Near-capacity tail
latency and saturated telemetry loss prevent treating peak throughput as an SLO.
The longer alternating comparison found no consistent write-CPU regression.

## Method and identity

- Four-vCPU x86_64 orb, Intel Xeon 2.60 GHz virtual CPU, 8,147,620 KiB RAM;
  Linux 6.1.189+, ext4 on virtual `/dev/vda`. This is not a physical-storage test.
- Rust 1.99.1, release/dev-feature binaries, oha 1.16.0, fd limit 100,000,
  `RUST_BACKTRACE` unset. No other builds, tests, agents or app services ran
  during measurements; platform services and the load generator share the VM.
- HTTP candidate: `e28573e`; its runtime is unchanged from the validated trim
  integration. `nanovm` SHA-256:
  `32942b71e04066eb5ba8948cf09af6987409a203bfafdf236ba67c19b411a6df`.
- Main-equivalent baseline: source identical to landed `ba87b87`, original
  release benchmark SHA-256
  `beefa385c6f9eb39be58b9fed64e9cff956ccd706602b007269dfccda0cfb80d`.
  Candidate comparison benchmark:
  `6e7adea3f44d9851572d6912b17ce757e0d4c04e10e488b5be0137ba5e182478`.
- Three HTTP rounds, fresh roots, six-second throughput measurements,
  fifteen-second offered-rate measurements. CPU is supervisor plus workers,
  plus proxy for proxy rows, sampled from `/proc`; client CPU is separate.
  Node/app retention, fixture identity and command lines are in raw records.
- Offered rates come from an independently completed three-round pilot with
  identical binaries: 90 valid measurements, 5,197,100 HTTP 200 responses and
  no transport errors. Only its rates calibrate the restarted full matrix;
  none of the stalled full attempt's rows enter the final tables.
- Ordinary HTTP has no active collector. Export measurements below are a
  separate **in-process** runtime plus decoding sink, not jailed HTTP capacity.

The full HTTP invocation was the protocol's `drive.py --rounds 3 --rates ...`,
followed by `summarize.py`. Its 240 records are valid across all three rounds:
90 direct, 72 fixed-rate, 36 proxy, six node-cold, six app-cold, three density,
and the in-process, cold-object, sync and start records. Measured status totals
are **16,617,893 HTTP 200 + 1,500 HTTP 204; zero transport errors**. Warmups and
setup requests are additional, not included in that total.

## Throughput is credible; leave latency headroom

Medians of three rounds, with throughput min–max in parentheses. Direct HTTP
uses a supervisor and jailed worker. Spread cases use 1,000 objects; c = clients.

| Direct workload | c | Requests/s | p50 ms | p99 ms | CPU µs/request |
|---|---:|---:|---:|---:|---:|
| Rust GET, spread | 64 | 27,372 (25,956–27,631) | 2.15 | 5.59 | 103.3 |
| Durable counter write, spread | 64 | 2,976 (2,877–3,028) | 20.90 | 44.06 | 821.2 |
| Durable counter write, one hot object | 64 | 822 (819–834) | 77.00 | 89.49 | 809.3 |
| JavaScript GET, spread | 64 | 11,857 (11,788–12,669) | 5.14 | 12.35 | 263.5 |
| JavaScript write, spread | 64 | 2,316 (2,261–2,419) | 26.70 | 58.05 | 1,150.2 |

Rust spread GET at c256 reached median 31,578/s (28,018–32,443); this is a
colocated-client saturation result, not a separately budgeted server capacity.
The single-object write bottleneck remains intentional serialization.

At offered 1,512 spread counter writes/s, achieved throughput is 1,512/s and
p99 is median 3.96 ms (3.56–4.33). At 2,419/s, p99 is 23.13 ms (10.14–35.40).
At 2,872/s, achieved throughput varies 2,698–2,871/s and p99 17.64–866.41 ms.
For Rust GET at offered 27,565/s, achieved throughput is only 23,074–25,985/s,
with p99 867–2,421 ms. The labels 50/80/95% mean fractions of **pilot** c64
throughput, not measured utilization. Never describe an unsustained offered
rate as successful service capacity. The generator competes for the same cores.

The full sequence follows cold-object traffic; the separate pilot is a simpler
warm workload. Do not silently pool their identities or treat every row as the
same steady-state workload. `/proc` accounting can miss workers exiting within
a sample; cold-start wall time is not inferred from that CPU counter.

## Proxy, startup and density

At c64, proxied Rust spread GET is median **19,193/s** (18,410–19,220), p99
6.86 ms, total CPU 156.8 µs/request. Proxied counter writes are **2,685/s**
(2,485–2,892), p99 49.58 ms, CPU 928.6 µs/request. Direct and proxy apps have
separate names and volumes, with equivalent fixtures. Full KV and JS rows
remain in the raw tables rather than extrapolated from Rust GET.

- Empty-data node startup to first successful counter response: median of
  per-round p50s **310 ms** (310–319); warm-data restart **71.2 ms** (69.2–73.1).
- App-worker restart with warm compile cache: **9.20 ms** (8.97–9.55);
  empty compile cache: **170 ms** (166–171). Thirty samples per variant/round.
- Each density round verified a stable target PID and fresh live/store counts
  **1 → 2,001 → 4,001 → 6,001**. Incremental slope: **120.3 KiB/object**
  (119.9–120.3), over an approximately 69 MiB seed-worker base. This validates
  density through 6,001 objects, not an arbitrarily larger-node extrapolation.
- All three syscall probes observed counter and KV writes at **2 fsync +
  3 fdatasync calls/request**. Read-only GET had no listed sync calls.
  These are syscall counts, not proven physical-device flush counts.

## The longer A/B comparison did not reproduce the short CPU warning

Three alternating fresh-process runs per binary, five repetitions each. Order
was baseline/current, current/baseline, baseline/current. Summarize each run by
its five-sample median, then show the median and range across the three runs.
All writes succeeded, including the composed SQLite `/set` workload. No trace
collector or remote acknowledgement was active in this comparison.

| In-process workload | Baseline CPU µs/request | Trim CPU µs/request |
|---|---:|---:|
| Serial GET | 65 (62–69) | 64 (63–65) |
| Serial counter write | 511 (495–517) | 479 (478–535) |
| Concurrent counter write | 632 (628–643) | 636 (620–640) |
| Serial SQLite/file/KV upsert | 1,289 (1,288–1,324) | 1,260 (1,254–1,324) |

The initial one-repetition comparison showed SQLite CPU 1,218 → 1,281 µs/request
(+5.2%). Keep that evidence, but it did not reproduce consistently in the longer
comparison. The overlapping ranges do not justify a performance improvement
claim either. Runtime source remains 8,331 lines, −490 versus the PR3 baseline.

## Full export has a lower lossless operating point

The original c256 export test **failed**: the candidate decoded
273,547/601,000 request spans, and the baseline 268,973/601,000. Successful
request throughput from those runs is not lossless-export throughput. Restricting
Tokio to one worker still failed (336,768/601,000). This is not a new trim
regression; the older 75–79k/s lossless claim did not reproduce here.

The benchmark now accepts `--export-concurrency N`; its default remains 256.
Zero, missing and nonnumeric counts are refused. No runtime queue, sampling,
batch size or mandatory span count was changed. Cold initialization also obeys
the chosen concurrency (up to its existing 64-client ceiling).

The measured operating points are:

| Export concurrency | Request rate | Decoded request spans | Result |
|---|---:|---:|---|
| 1 | 18,277/s | 601,000/601,000 | Complete single probe |
| 2 | 32,731/s | 601,000/601,000 | Complete single probe |
| 3 | 54,542/s (51,608–54,676) | 1,803,000/1,803,000 over three invocations | Complete |
| 4 | 103,355/s | 472,849/601,000 | Incomplete; excluded from lossless claims |
| 256 | 105,084/s | 273,547/601,000 | Incomplete; excluded from lossless claims |

At c3, throughput **including shutdown/export drain** is median **54,100/s**
(51,184–54,214). Each invocation decodes all 601,000 request spans, not merely
successful HTTP exports. The decoding sink shares this process and these cores;
this does not establish production Collector or jailed HTTP/export capacity.
The CLI update changes only the benchmark example; the measured runtime binary
and A/B binaries are unchanged.

Reproduce the export operating point after the fresh release build:

```sh
env -u RUST_BACKTRACE cargo run --locked --release -p nanovm --features dev \
  --example bench -- --export --export-concurrency 3
```

## Limits and retained evidence

physical power loss, sustained production load, unbounded tenant counts, or
survival of every aggregate hostile proxy-buffer workload. Local multi-node,
disk and OOM correctness evidence is in `../trim-integration.md`.

probes and the short/long A/B comparisons are retained with the thread's
